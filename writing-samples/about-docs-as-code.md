# About Docs as Code

Docs as Code refers to a documentation workflow that applies the same development practices, standards, and review processes that software engineers use when working with code. The docs-as-code workflow is common because it provides a frictionless way for software engineers and technical writers to contribute to a set of documentation in a repository.

The benefits of this workflow includes the following:

* Work with the same tools you use to write and manage code.
* Keep documentation in sync with the code.
* Track changes through version control and maintain a history of updates.
* Review documentation changes through pull requests, just like code.
* Maintain documentation standards through automated checks (such as linters for grammar, spelling, and style).
* Automate documentation builds and publishing.

The following description and diagram show a simplified workflow of the docs-as-code toolchain:

1. **Make changes**: Add or update documentation in your GitHub repository.
2. **Open a pull request**: Propose your changes for review.
3. **Get feedback**: Collaborate with your team and incorporate feedback.
4. **Merge**: Combine approved changes into the main branch.
5. **Publish**: Deploy your documentation to your website.

![alt_text](images/dac-workflow.png "workflow")

The process is iterative, meaning you can continue making improvements as your documentation evolves.

## Is Docs as Code right for your organization?

Docs as Code works particularly well when documentation is closely tied to software development and software engineers are expected to contribute to the documentation. This workflow provides all contributors with a familiar workflow while allowing teams to apply the same quality standards and collaboration practices to documentation that they use for code. Technical writers don’t need to become software engineers, however, they do need to have an understanding of the various tools used in a docs-as-code workflow.
